The T4 outlier that wasn't model latency

a 1000s+ duration spike, reproduced N=3, traced to the wrong cause on the first pass

arm4 (Opus) and arm6 (Sonnet+advisor) each hit a T4 duration ~10× every other arm (1062s / 1330s) while diff size and toolcalls stayed normal — first written up as "model wall-clock latency." An N=3 repeat with raw transcript timestamp analysis found the gap sits precisely between the PreToolUse:Bash and PostToolUse:Bash hook events — i.e. human bash-approval wait time, not model processing.

arm4 reproduced 3/3 (20–74 min gaps). arm6 reproduced 0/3 (86–99s, normal) — the original arm6 reading was a one-off session artifact, not a condition effect. The hypothesis was retracted in the results doc alongside the repeat data that disproved it.

Source: results-summary-6arm.md, "T4 시간축 이상치" section.

Limits / not proven

  • No quality axis was measured. Judgment tasks (T3) were never scored for output quality by a human or a separate judge — "which model writes better" has no evidence here.
  • The four measured axes rank oppositely depending on the goal. Delegation rate favors advisor=on; token cost and speed favor advisor=off. There is no unified cost metric to resolve this into a single ranking.
  • Almost everything is N=1. Outside the baseline triplicate (arm1/3/5), every arm ran once — repeat runs would raise confidence, not create a quality axis or a unified metric that doesn't exist.
  • Task scope is trivial-to-medium only. Whether this generalizes to production-scale tasks is untested — delegation could plausibly become net-positive at larger scale.
  • Session independence isn't absolute. A global hook plugin (claude-smart) was found observing and re-injecting rules across supposedly isolated benchmark sessions — relative arm comparisons hold, but "fully independent observation" doesn't.
