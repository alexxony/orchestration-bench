# 오케스트레이션 비용 모델 · 모델 판별 테스트

멀티에이전트 운용(Fable 오케스트레이터 + Sonnet executor)의 비용 구조 관측과
개선 방향. 이 저장소의 위임 정책(hookify 룰 2종 + delegation-reminder.py)을
비용 축에서 뒷받침하는 근거 문서. 원 출처: Compiler_Thermal P8 실측 세션
관측(2026-07-15~17).

---

## 관측 데이터 (2026-07-14~17, 실측)

| 관측 | 수치 | 함의 |
|---|---|---|
| 위임 룰 적용 전 Fable output 비중 | 75.6% | 오케스트레이터 과로 — 91% 크레딧 사고의 구조 |
| 룰 적용 후 (2026-07-15) | Fable out 58.8%, 실질(noncache) 소비 Sonnet 72% | 위임 구조 건전 판정 |

2026-07-17 세션 재확인: executor가 상태 변화 없는 idle 알림으로 오케스트레이터를
3회 깨움 — 각 깨우기마다 디스크 포렌식 왕복 발생. 반대 사고도 같은 세션에서
관찰: 착수 직후 무보고 유휴 → 오케스트레이터가 "미착수" 오판(실제로는
백그라운드 정상 가동). 양쪽 다 **executor 보고 프로토콜 부재**가 원인.

## 즉시 적용 정책 (spawn 프롬프트 표준)

1. **마일스톤·이상 시에만 SendMessage** — idle 전환 자체는 알림 사유 아님.
   "조용한 유휴 금지"와 결합: 유휴로 빠지려면 반드시 직전에 상태 보고를 남긴다.
2. **백그라운드 착수 시 착수 보고 의무** — "pid N으로 X 시작, 다음 보고는
   Y 시점" 형식. 오케스트레이터의 생사 오판(미착수 vs 가동 중)을 차단.
3. **spawn에 `model=sonnet` 명시** — 미지정 시 Opus 쏠림 실측됨. 예외(opus)는
   아키텍처·고난도 구현만.
4. **장기 감시는 monitor로 배선** — 오케스트레이터 직접 폴링 금지. 파일
   생성/프로세스 생사/OOM 같은 상태 전환만 이벤트로 수신.
5. **상태 파일 이중화** — executor는 대화 보고와 별개로 디스크 상태 파일
   (`*_status.md`)을 갱신. 세션 유실 시 포렌식 단일 소스.

## 모델 판별 테스트 (미실행, 설계 고정)

**질문**: 오케스트레이터 품질이 모델(Fable)에 의존하는가, 공정(하니스)에
정착했는가.

**설계**: 다음 프로젝트 설계 국면을 Opus 오케스트레이터(fast mode)로 시도 +
동일 방식 토큰 집계 재실행.
- Fable output 비중 70%대로 상승 → 공정이 모델에 의존 (Fable 유지)
- 55~60% 유지 → 노하우가 하니스에 정착 (모델 다운그레이드 가능)

**후속 함의**: "정착" 판정이면 LLM 제공자 마이그레이션 경로(Claude →
OpenAI 호환 저비용 API → 로컬 vLLM/Ollama)의 첫 관문 통과. 하니스 = 위임
정책(이 저장소) + spawn 표준(위) + 프로젝트별 6단계 루프이며, 이 부품들은
모델 중립이다.

### 2026-07-25 관측 — 세션 모델 Sonnet 전환

- 사용자가 이 세션에서 `/model` 명령으로 오케스트레이터 모델을 Opus에서
  Sonnet으로 변경함 (advisor는 별도로 Opus 5 유지).
- 기존 모델 판별 테스트 설계는 "Opus 오케스트레이터로 시도 + 동일 방식
  토큰 집계 재실행"을 전제로 함 — 이번 관측은 그 설계와 다름. 오케스트레이터가
  이미 Sonnet이라 Opus vs Sonnet 비교 축 자체가 사라짐.
- **함의**: 오케스트레이터=executor 모델 티어가 같아지면(Sonnet=Sonnet),
  위임의 핵심 근거였던 "고비용 모델 과로 방지"(75.6%→58.8% 개선 수치의
  전제)가 약화됨. 트리비얼~중간 난이도 작업은 위임 오버헤드(spawn+통신
  프로토콜 준수 비용)가 이득을 상쇄할 가능성.
- 통신·신뢰성 규칙(재위임 금지, 디스크 우선 검증, monitor 폴링 위임)은
  모델 무관하게 유효하다는 점은 유지.
- **결론**: "정식 모델 판별 테스트"는 아직 미실행 상태로 남김(원설계=Opus
  오케스트레이터 필요). 이번 기록은 참고 관측일 뿐.

## 미해결

- 깨우기 1회당 비용의 정량 모델(캐시 TTL·컨텍스트 크기 함수) — 세션 리포트
  집계로 산출 가능, 아직 미실행.
- executor 보고 프로토콜의 hookify 룰화(경고 수준) 여부 — 현재는 spawn
  프롬프트 수동 명시에 의존.
