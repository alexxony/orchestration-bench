# 사고 사례집 (Incident Casebook)

> 에이전트 오케스트레이션 실전 사고 기록. 목적: 같은 계열 오류의 재발 방지 규칙 도출.
> 형식: 증상 → 오판 경로 → 발각 계기 → 비용 → 도출 규칙.
> 원본 증거는 각 프로젝트 code repo JOURNAL.md / vault PROGRESS.md — 여기선 커밋 해시로 참조만(중복 서술 금지).
> 자매 문서: [verification-gates.md](verification-gates.md) (사례에서 도출한 원칙 모음),
> [orchestration-cost-model.md](orchestration-cost-model.md) (비용 모델).

## 분류

- **A형 — 조용한 오판**: 에이전트가 자신 있게 틀린 결과를 내고, 검증 없이 문서/판정에 유입. 최고 비용 계열.
- **B형 — 통신·생존 사고**: 에이전트 죽음, 보고 유실, 세션 컷오프. 인프라(원장·autosave·디스크 선검증)로 완화됨.
- **C형 — 기록 사고**: 미커밋 유실. JOURNAL 원장 관례(2026-07-18)로 종결된 계열.

## A형 — 조용한 오판

### C1. 통계 리포터 부호 버그 — 35문제 판정 전체 오염 (Compiler_Thermal, 2026-07-18~19)

- **증상**: P8 규모 확장 ablation 결과 "compute-bound gain 전무(M1≡1.00, 재현율 0%)" — 공식 판정 v2로 확정·문서화됨.
- **오판 경로**: `report_p8_stats.py`가 metric_curve(-energy 규약, 클수록 좋음)에서 `best=min()`으로 선택 → best가 항상 seed → M1이 구조적으로 1.00 고정. **selfcheck가 양수 energy 곡선(happy-path)만 검사해 버그를 은폐.** 오판 위에 후속 조사(P9-A 원인 분석)까지 쌓임 — (b)/(c)/(d) 분류 전체가 버그 파생.
- **발각 계기**: 별건 스팟체크(ncu 커널 디스패치 비교)에서 "TF32 유효"가 확인되자 M1=1.00과의 모순 추적 → 원시 metric_curve 직접 열람으로 gain 실재 확인.
- **비용**: 하루 이상 공식 결론이 정반대("gain 전무" ↔ 실제 matmul 7건 2.61~6.00×). 후속 조사 문서 오염, 재판정 v3·방법론 재검토 v4까지 연쇄 재작업.
- **도출 규칙**: ① 개선 곡선(seed≠best) 케이스 없는 selfcheck는 무효 — 음성/개선 케이스 필수. ② 부호 규약(higher/lower=better)은 소비 코드에서 하드코딩하지 말고 저장 규약 문서와 대조. ③ 통계 파이프라인의 최종 방어선은 원시 데이터 스팟 대조. 수정 커밋 `e63e16d`(compiler_thermal/loop).

### C2. "동일 파일" 오판 — diff 한 번이면 잡혔을 주장의 생존 (Compiler_Thermal, 2026-07-18~19)

- **증상**: P9-A 원인 조사 문서가 "1_Square는 variant=seed 완전 동일 파일"이라 단정 — 이후 v3에서 M1 5.77×가 나오자 "동일 파일인데 개선?"이라는 가짜 미스터리가 생겨 ncu 프로브(A100 과금)까지 계획됨.
- **오판 경로**: 조사 에이전트가 diff를 실제로 실행했는지 불명(했다면 잘못된 경로 대상). 검증 없이 문서화 → 다음 세션들이 "사실"로 소비.
- **발각 계기**: 후속 설계 검토(planner)가 재-diff로 상이 확인 → 팀리드가 diff 재실행 + git log(두 파일 모두 조사 이전부터 무변경)로 독립 검증 — "조사 시점에 이미 달랐다" 확정.
- **비용**: 가짜 미스터리 1건이 open-questions에 등재, 시드 전수 재검사 우선순위 왜곡, 불필요한 A100 프로브 계획.
- **도출 규칙**: ① 파일 동일성 주장은 diff 출력(또는 sha256)을 증거로 문서에 첨부해야 유효. ② 에이전트 조사 문서의 핵심 주장은 소비 전 1회 독립 재현. ③ 오판 1건 발견 시 같은 문서의 형제 주장 전수 재검토(실제로 retire 4→3건 오기 추가 발견).

### C3. 부분 열람 오판정 — CSV 앞 50행만 보고 "무효" 선언 (HBM_build, 2026-07-19)

- **증상**: P4 T4 3D-ICE 결과물(6케이스)이 "s0/s1/s2 완전 동일 = 무효"로 판정됨(커밋 36efed3 저자).
- **오판 경로**: CSV 앞 50행(비-base_die 항목)만 열람 — 그 구간은 설계상 시나리오 불변이 정상. `.stk` diff exit=0도 무효 신호로 오독(전력은 `.flp` 책임, `.stk`는 구조만). 부분 데이터에서 전체 결론.
- **발각 계기**: 재조사에서 base_die_phy 행 직접 열람(180.15→199.16→212.24°C 단조 증가) + `.flp` 원시 출력 교차검증 + 오케스트레이터 독립 포렌식(mtime 타임라인, 덮어쓰기 부재) — 결과물 유효로 재확정.
- **비용**: 유효 결과물 폐기 위기(재실행이면 라이선스 제약 환경에서 고비용), 무효 판정→정정 왕복.
- **도출 규칙**: ① "동일/무효" 판정은 차이가 나야 할 필드를 특정하고 그 필드를 직접 열람한 후에만. ② 설계 문서(어떤 축이 무엇에 영향 주는지)와 대조 없이 "변화 없음=버그" 단정 금지. ③ 폐기·재실행 결정 전 독립 포렌식 1회.

### C4. 오진 연쇄 — misleading 로그 + 삼켜진 예외가 만든 가설 소모전 (HBM_build, 2026-07-18~19)

- **증상**: Icepak 캠페인 A-S1이 5초 즉시 실패(`Design setup None solved correctly in 0.0h 0.0m 5.0s`). "타이밍/레이스" → "결정론적 코드 버그" → "power_scenario 값 의존" 가설이 차례로 세워지고 재시도·진단 캠페인 소모.
- **오판 경로**: 두 겹의 은폐 — ① 프레임워크 로그가 misleading("Design setup None"은 실패 원인이 아님), ② pyaedt가 네이티브 오류를 삼킴. 보이는 정보만으로 가설을 쌓아 전부 빗나감.
- **발각 계기**: `GetMessages()` 계측 추가(53d0460) 후에야 원문 회수 — `Maximum licensed number of demo users already reached` → **진범 = demo 라이선스 시트 고갈**. 대조 실험(A-S0 재실행 동일 실패)으로 "환경 전체 고착" 확정, 국지 가설 전부 반증.
- **비용**: 재시도 한도 소진, 진단 캠페인 수 시간, 가설 3개 폐기. 최종 해법은 콜드 셧다운(코드와 무관).
- **도출 규칙**: ① 래퍼가 예외를 삼키는 환경(pyaedt 등)에선 네이티브 오류 회수 계측을 가설 수립 **전에** 넣는다 — 계측 비용 < 빗나간 가설 1개 비용. ② 같은 커맨드의 과거 성공 이력이 있으면 "코드 버그" 가설보다 "환경 변화" 가설을 먼저 검증(대조 재실행). ③ misleading 로그 문자열은 원장에 "오도 주의"로 명기해 다음 세션의 재오진 차단.

## B형 — 통신·생존 사고 (완화됨 — 대응 패턴 확립)

### C5. 완료 알림 유실 → 3.4h 무진행 + 결과 유실 (Compiler_Thermal, 2026-07-18)

- **증상**: executor가 원격 런 완료를 놓치고 3.4시간 방치, fetch 전 colab 세션 idle 소멸로 결과(구제 런1) 유실.
- **원인**: 완료 알림이 하네스 단에서 유실 — 재확인 트리거 부재. fetch 성공 후 로컬 저장이 호출자 관례에 위임돼 있던 유실 창.
- **대응(구조화됨)**: 러너 autosave(`4435c6b` — fetch 즉시 무조건 로컬 보존), 원격 발사·회수는 오케스트레이터 직접, 디스크 증거 우선 원칙.
- **도출 규칙**: ① 알림은 at-most-once로 가정 — 원격 유일 사본 상태를 허용하는 창을 코드에서 제거. ② 워커 상태 판단은 보고가 아니라 디스크(커밋·산출물 mtime).

### C6. 무보고 idle — 보고 규약 미준수의 반복 (Compiler_Thermal, 2026-07-19 × 2회)

- **증상**: 서브에이전트(scientist 1회, executor 1회)가 최종 보고 없이 idle 전환. executor 건은 Task 41 산출물·코드가 디스크에 있으나 미커밋 + 테스트 숫자 미보고 상태.
- **대응**: 디스크 선검증(git log·산출물 판독)으로 실제 진척 확인 → 마무리 지시 1회로 회수. 데이터 손실 0, 복구 수 분.
- **도출 규칙**: ① idle 알림 수신 시 "보고 왔나?"가 아니라 "디스크에 뭐가 있나?"부터. ② 위임 프롬프트에 완료 조건(테스트 숫자·커밋·보고 4항)을 명시해도 미준수 발생 — 회수 절차(디스크 검증→마무리 지시)를 표준으로 유지. 근본 해결(보고 강제 장치)은 미해결 과제.

## 사례 추가 절차

1. 사고 발생 프로젝트의 JOURNAL에 먼저 기록(원장 우선).
2. 여기엔 분류(A/B/C) + 5요소(증상/경로/계기/비용/규칙)로 압축, 원본은 커밋 해시 참조.
3. 도출 규칙이 기존 verification-gates.md 원칙과 겹치면 원칙 쪽에 사례 링크만 추가, 새 원칙이면 양쪽 갱신.
